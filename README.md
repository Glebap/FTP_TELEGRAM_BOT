# 🎾🥎🏸 Sport Partner Bot

Telegram-бот для поиска партнёра по спорту. UX как в «Дайвинчике», но цель другая:

**Профиль → Поиск → Карточка игрока → Следующий / Написать**

Поддерживаются **теннис** (шкала NTRP), **падел** и **бадминтон** — у каждого своя шкала уровней
и свой тест из 10 вопросов. Новый вид спорта добавляется записью в конфиге, без правок
в бизнес-логике. Один пользователь может играть в несколько видов: поиск, уровни, история
просмотров и уведомления считаются по каждому отдельно.

Стек: **TypeScript + Node.js + Telegraf 4 + Prisma**. По умолчанию база — SQLite (запуск без Docker),
для продакшена в комплекте PostgreSQL + Docker Compose.

---

## Быстрый старт (без Docker)

```bash
npm install
cp .env.example .env          # вставьте BOT_TOKEN от @BotFather
npm run setup                 # prisma generate + db push + сид спортов и квиза
npm run dev
```

`.env` минимально:

```env
BOT_TOKEN=123456:ABC-DEF...
DATABASE_URL="file:./dev.db"
ADMIN_IDS=123456789           # ваш Telegram ID, чтобы работала /admin
```

Дальше — `/start` в чате с ботом.

## Деплой

Боевой деплой описан в [DEPLOY.md](DEPLOY.md) — Fly.io, одна машина, SQLite на постоянном
диске. Ниже — альтернативный вариант с PostgreSQL в Docker Compose.

## Запуск в Docker (PostgreSQL)

1. В `prisma/schema.prisma` поменяйте провайдер:

   ```prisma
   datasource db {
     provider = "postgresql"
     url      = env("DATABASE_URL")
   }
   ```

2. Пересоздайте миграции под Postgres (SQLite-миграции несовместимы):

   ```bash
   rm -rf prisma/migrations
   npx prisma migrate dev --name init     # при поднятом Postgres
   ```

3. Заполните `BOT_TOKEN` в `.env` и поднимите всё одной командой:

   ```bash
   docker compose up --build
   ```

Контейнер бота сам применяет миграции и запускает сид перед стартом, так что свежая база
готова к работе сразу.

│   ├── sportsPadelBadminton.ts  падел и бадминтон
│   ├── geo.ts           поведение выбора страны и города

│   ├── geoService.ts      поиск страны и города с исправлением опечаток
│   ├── quizService.ts     прохождение и сохранение теста
│   ├── userService.ts     профиль, уровень, скрытие, удаление
│   ├── contactService.ts  контакты и лимиты
│   ├── digestService.ts   кому и о чём слать рассылку

├── bot/

│   ├── flow.ts        экраны регистрации и навигация назад/вперёд
│   ├── apply.ts       единая точка записи значения (черновик или БД)
│   ├── ui.ts          отправка/редактирование экрана
│   ├── digest.ts      текст рассылки и её отправка
│   ├── scheduler.ts   cron-задачи рассылки
│   ├── keyboards/     все клавиатуры
│   ├── views/         рендеринг карточек профиля
│   ├── middlewares/   ошибки, троттлинг, загрузка пользователя
│   └── handlers/      start, registration, quiz, search, profile, settings, admin, input

Две вещи, на которые стоит обратить внимание при доработке:

- **`bot/apply.ts`** — регистрация и правка одного поля используют один код записи, поэтому
  два потока не могут разойтись в поведении.
- **Сессии в БД** — незаконченная регистрация переживает перезапуск бота (в отличие от
  стандартного in-memory хранилища Telegraf).

## Как настраивать без правок кода

**Область поиска** — `src/config/matching.ts`, `defaultScope`. По умолчанию `'city'`: партнёры
ищутся только в городе пользователя. Значение `'any'` сняло бы фильтр совсем.

**Веса матчинга** — `src/config/matching.ts`:

```ts
sameCity: 40,
sameCountry: 20,
levelDifference: [{ maxDiff: 0, points: 25 }, { maxDiff: 0.5, points: 20 }, ...],
ageDifference: [{ maxDiff: 3, points: 10 }, { maxDiff: 7, points: 5 }],
```

**Вопросы квиза и mapping уровня** — `src/config/sports.ts`, затем `npm run db:seed`
(сид идемпотентный: правка вопроса обновляет запись, а не плодит дубликаты).

**Новый вид спорта** — добавить объект в `sports` (`slug`, уровни, `levelTolerance`, квиз,
`isActive: true`) и выполнить `npm run db:seed`. Шаг выбора спорта в регистрации появляется
сам, как только активных спортов больше одного. Теннис описан в `sports.ts`, падел и
бадминтон — в `sportsPadelBadminton.ts` (они делят описательную шкалу 1–5).

## Где именно ищутся партнёры

Город — **жёсткий фильтр**, а не бонус к рейтингу. Игрок из другого города не тот, с кем можно
выйти на корт, поэтому подмешивать его в выдачу значит тратить нажатия пользователя.

```text
🎾 Больше некого показать в Chisinau

Вы посмотрели всех подходящих игроков в Chisinau.

Можно посмотреть игроков из других городов — но играть с ними будет сложнее.
[🌍 Искать в других городах]
[🔄 Смотреть заново]
[🏠 В меню]
```

Расширить область можно только явной кнопкой. После неё фильтр по городу снимается, но scoring
всё равно ставит вперёд свою страну и близкий уровень, а уже просмотренные профили остаются
исключёнными — поиск продолжается с того места, где закончился локальный.

Сравнение городов идёт по `cityGeonameId` из справочника, поэтому «Кишинёв» и «Chisinau» — один
город. Совпадение по строке используется как запас для записей, созданных до появления справочника.

Внутри города остаётся всё остальное: допуск по уровню из конфига спорта, отсутствие уже
просмотренных, скрытые профили, и сортировка по совместимости.

## Несколько видов спорта у одного пользователя

При регистрации человек выбирает один вид спорта и указывает уровень по его шкале. Дальше
в «👤 Мой профиль → 🏆 Виды спорта и уровни» можно добавить остальные, поменять уровень
каждого или убрать лишний (последний убрать нельзя — профиль без спорта бесполезен).

Всё, что связано с подбором, считается **по каждому спорту отдельно**:

- поиск спрашивает, по какому виду искать, если их больше одного;
- допуск по уровню берётся из конфига этого спорта (`levelTolerance`);
- «просмотренные» профили запоминаются отдельно (`ProfileView` хранит `sportId`), поэтому
  один и тот же человек может встретиться и в теннисе, и в падле;
- контакты помнят, из какого спорта они пришли;
- рассылка проверяет каждый вид спорта и присылает разбивку, если новые игроки есть в нескольких.

Первый выбранный спорт остаётся основным (`UserSport.isPrimary`) — он используется по умолчанию,
когда спорт явно не выбран.

Шкалы уровней разные и намеренно не сводятся к одной: NTRP 2.5–4.5+ для тенниса, описательная
«новичок → продвинутый» для падла и бадминтона, потому что общепринятого рейтинга для них
в регионе нет и новичок просто не сможет ответить, какой у него «NTRP по падлу».

**Лимиты антиспама** — `.env`: `SEARCH_LIMIT_PER_MINUTE`, `CONTACT_LIMIT_PER_MINUTE`,
`CONTACT_LIMIT_PER_DAY`.

**Возраст** — `src/config/profile.ts`: `minAge` / `maxAge` (границы только против опечаток,
возрастного порога нет) и `quickAgeRange` для кнопок.

**Страны и города** — `src/config/geo.ts`: какие страны показывать кнопками, сколько давать
подсказок, сколько крупных городов предлагать.

## Рассылка «новые игроки в городе»

Дважды в день (по умолчанию **10:00** и **19:00**, `Europe/Chisinau`) бот проверяет, не появились
ли у человека новые подходящие партнёры, и пишет только если появились:

```text
🎾 3 новых игрока в Chisinau

Andrei, Victor, Sergiu

Загляните в поиск — возможно, это ваш партнёр по игре.
[🎾 Посмотреть] [🔕 Не присылать]
```

Игрок попадает в счётчик, только если выполнено всё сразу:

- зарегистрировался **после предыдущей рассылки** этому пользователю (первая рассылка смотрит
  назад не больше `maxLookbackDays`, по умолчанию 14 дней);
- **тот же город** (сравнение по `cityGeonameId`, а не по строке);
- **подходящий уровень** — тот же фильтр допуска, что и в поиске;
- пользователь его **ещё не видел** в поиске;
- профиль активен и не скрыт.

Если ничего нового нет — сообщение не отправляется вообще. После успешной отправки в
`lastDigestAt` пишется момент рассылки, поэтому одни и те же игроки не приходят дважды.

Пользователь может отключить рассылку кнопкой «🔕 Не присылать» прямо в сообщении или в
«⚙️ Настройки». Если человек заблокировал бота, Telegram отвечает 403 — рассылка для него
выключается автоматически.

Настройки в `.env`:

```env
DIGEST_ENABLED=true
DIGEST_TIMES=10:00,19:00
DIGEST_TIMEZONE=Europe/Chisinau
```

Админские команды для проверки: `/digest_preview` — кто получит и сколько, без отправки;
`/digest_send` — отправить немедленно и показать итог.

## Справочник стран и городов

Свободный ввод города исключён: пользователь всегда выбирает запись из справочника, поэтому
два игрока из одного города никогда не окажутся в разных «городах» из-за опечатки. В базе
хранится и каноническое название, и `cityGeonameId` — matching сравнивает города по id.

Как бот понимает ввод:

| Пользователь написал | Результат |
| --- | --- |
| `Україна`, `украина`, `Ukraina`, `УКРАИНА` | Принято сразу — все варианты сводятся к одному ключу |
| `Укрна`, `Кишенев` | «Не нашли точного совпадения. Вы имели в виду:» + кнопки с вариантами |
| `асдасдасд` | «Страны «асдасдасд» не существует» / «не нашли город» + список для выбора |

Работает это за счёт нормализации в [geoNormalize.ts](src/utils/geoNormalize.ts): снимаются
диакритика (`Chişinău` → `chisinau`), украинские и белорусские буквы сводятся к русским
(`і`→`и`, `є`→`е`, `ё`→`е`), затем ищется точное совпадение, затем совпадение по началу слова,
затем расстояние Левенштейна в пределах бюджета опечаток (примерно треть длины запроса).

Данные: **210 стран** и **67 663 города** из дампа GeoNames `cities1000` (CC BY 4.0) плюс
названия стран на 11 языках из `i18n-iso-countries`. Города разложены по файлам
`src/data/cities/<CC>.json` и подгружаются лениво — поиск всегда идёт внутри уже выбранной
страны, поэтому в памяти держится только несколько стран.

Покрытие по населению задано в [scripts/build-geo-data.ts](scripts/build-geo-data.ts):

- Молдова, Украина, Румыния, Польша, Балканы, СНГ, Израиль, Турция — **все города** из дампа
  (в Молдове это 98 городов, включая Кагул и Рыбницу);
- Западная Европа и Северная Америка — от 5 000 жителей;
- остальной мир — от 15 000 жителей.

Обновить справочник: `npm run build:geo` (скачает дамп в `.cache/`, перезапишет `src/data`).
Сгенерированные файлы лежат в репозитории, при обычной сборке ничего не скачивается.

Названия городов показываются в канонической латинице из GeoNames (`Chisinau`, `Kyiv`,
`Moscow`), а искать можно на любом языке. Альтернативные названия в кириллице в данных есть,
но в них попадают исторические и шуточные варианты («Донбас-сіті», «Свердловск»), поэтому для
отображения берётся только основное имя. Если нужен вывод на русском — это правка одной
функции в генераторе.

### Тесты

- `tests/scoring.test.ts` — приоритет «свой город > своя страна > остальные», деградация бонуса
  за разницу уровня и возраста, стабильная сортировка.
- `tests/quiz.test.ts` — mapping из §12, монотонность (больше баллов не даёт уровень ниже),
  результат всегда попадает в список уровней спорта.
- `tests/geo.test.ts` — `Україна` == `Украина`, опечатки дают подсказки, бессмыслица не даёт
  ничего, город одной страны не находится в другой, все написания «Кишинёва» ведут в одну запись.
- `tests/digest.test.ts` — в счётчик попадают только новые игроки того же города и уровня,
  повторно те же не приходят, отключённые уведомления и скрытый профиль исключают из рассылки.
- `tests/matching.integration.test.ts` — просмотренные не возвращаются, скрытые профили
  исключаются, допуск по уровню работает как жёсткий фильтр, данные живут после переподключения.
- `tests/registration.flow.test.ts` — полный путь пользователя: регистрация, квиз, карточка
  партнёра, контакт, скрытие профиля, правка одного поля, удаление аккаунта, «мёртвая» кнопка,
  а также подсказки и отказы на шагах страны и города.

## Эксплуатация

- Ошибки Telegram API вида «message is not modified» и «query is too old» гасятся молча,
  остальное логируется через pino и не роняет бота.
- Логи: `LOG_LEVEL` (`info` по умолчанию, в dev — pino-pretty).
- Секреты только в `.env` (в git не попадает), `.env.example` — шаблон.
- Бот работает на long polling; для вебхуков нужен публичный HTTPS-эндпоинт и правка `main.ts`.
